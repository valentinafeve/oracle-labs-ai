## 2.3 Transformar staging -> tabla final

```sql
INSERT INTO ADMIN.LAB202_MATCH_FACT (
  HOME_TEAM_NAME, AWAY_TEAM_NAME,
  HOME_TEAM_ID, AWAY_TEAM_ID,
  HOME_TEAM_GOALS, AWAY_TEAM_GOALS,
  DATE_RW, REFEREE, VENUE_NAME, VENUE_CITY
)
SELECT
  TEAM_HOME_NAME,
  TEAM_AWAY_NAME,
  TO_NUMBER(TEAM_HOME_ID DEFAULT NULL ON CONVERSION ERROR),
  TO_NUMBER(TEAM_AWAY_ID DEFAULT NULL ON CONVERSION ERROR),
  TO_NUMBER(SCORE_HOME DEFAULT NULL ON CONVERSION ERROR),
  TO_NUMBER(SCORE_AWAY DEFAULT NULL ON CONVERSION ERROR),
  CASE
    WHEN MATCH_DATE IS NOT NULL AND MATCH_TIME IS NOT NULL THEN
      TO_TIMESTAMP_TZ(
        MATCH_DATE || ' ' || MATCH_TIME || ' +00:00',
        'DD-MON-RR HH24:MI:SS TZH:TZM',
        'NLS_DATE_LANGUAGE=ENGLISH'
      )
    WHEN MATCH_DATE IS NOT NULL THEN
      TO_TIMESTAMP_TZ(
        MATCH_DATE || ' 00:00:00 +00:00',
        'DD-MON-RR HH24:MI:SS TZH:TZM',
        'NLS_DATE_LANGUAGE=ENGLISH'
      )
    ELSE NULL
  END,
  CAST(NULL AS VARCHAR2(64)),
  VENUE,
  CAST(NULL AS VARCHAR2(64))
FROM ADMIN.LAB202_MATCH_STG;

COMMIT;
```

## 4) Construcción del flujo (arquitectura robusta)

Nodos:
1. `Chat input`
2. `Prompt` (SQL)
3. `LLM`
4. `Type Convert` (o `Type Converter`)
5. `Parser`
6. `SQL query`
7. `Prompt` (respuesta)
8. `Agent`
9. `Chat output`

Contrato de datos entre nodos:
1. `Chat input.Message`: pregunta del usuario (texto).
2. `LLM.Message`: texto con JSON (`query`, `safe`, `reason`).
3. `Type Convert.JSON`: objeto JSON parseable.
4. `Parser*.Message`: valor extraído por parser (`query` o `safe` o `reason`).
5. `SQL query.JSON`: resultado tabular de la consulta.
6. `Agent.Message`: respuesta final en lenguaje natural.

Objetivo de cada módulo:
1. `Chat input`: capturar la pregunta.
2. `Prompt SQL`: forzar salida estructurada y segura.
3. `LLM`: generar JSON con SQL y metadatos de seguridad.
4. `Type Convert`: pasar de texto a JSON.
5. `Parser`: extraer campos puntuales del JSON.
6. `SQL query`: ejecutar la SQL en `ADMIN.LAB202_MATCH_FACT` vía Data Source.
7. `Prompt final`: consolidar pregunta, SQL y resultados.
8. `Agent`: redactar respuesta final.
9. `Chat output`: presentar la respuesta.

## 4.1 Prompt SQL (estricto)
Para que se usa:
- Definir reglas para que el LLM devuelva SQL seguro y parseable en JSON, evitando salida libre o comandos no permitidos.

Que recibe:
- La pregunta del usuario desde `Chat input.Message`.

Que entrega:
- `Prompt message` con instrucciones completas para el LLM.

Como configurarlo:
- Usa el template de esta sección y conecta `Chat input.Message` a la variable `question`.

Template:

```text
You are an Oracle SQL generator for football match analytics.

Question:
{{question}}

Use only table ADMIN.LAB202_MATCH_FACT and only these columns:
HOME_TEAM_NAME, AWAY_TEAM_NAME, HOME_TEAM_ID, AWAY_TEAM_ID,
HOME_TEAM_GOALS, AWAY_TEAM_GOALS, DATE_RW, REFEREE, VENUE_NAME, VENUE_CITY

Output ONLY valid JSON with this exact schema:
{
  "query": "<SQL>",
  "safe": true,
  "reason": "<short reason>"
}

Rules:
1) query must be exactly one SELECT statement.
2) query must start with SELECT.
3) No semicolon.
4) No markdown, no comments, no extra text.
5) Never generate DML/DDL/PLSQL.
6) Reject these tokens: INSERT, UPDATE, DELETE, MERGE, DROP, ALTER, BEGIN, DECLARE.
7) For non-football questions:
   query = SELECT 'Only football questions are supported' AS mensaje FROM DUAL
   safe = false
8) For exploratory list queries add ORDER BY + FETCH FIRST 20 ROWS ONLY.
```

Conexión:
- `Chat input.Message` -> variable `question` del Prompt SQL.

## 4.2 LLM
Para que se usa:
- Generar la salida estructurada (`query`, `safe`, `reason`) que alimenta la ejecución SQL.

Que recibe:
- `Prompt SQL.Prompt message`.

Que entrega:
- `LLM.Message` (texto JSON).

Como configurarlo:
- Modelo `openai.gpt-oss-120b (oci)`, `Temperature = 0.01`.

1. Modelo: `openai.gpt-oss-120b (oci)`.
2. Temperature: `0.01`.
3. Conecta `Prompt SQL.Prompt message` -> `LLM.Prompt`.

## 4.3 Type Convert / Type Converter
Para que se usa:
- Convertir la respuesta textual del LLM en un objeto JSON confiable para parsing.

Que recibe:
- `LLM.Message` (string).

Que entrega:
- `Type Convert.JSON` (objeto JSON).

Como configurarlo:
- Conversión `String -> JSON`.

2. Conversión: `String` -> `JSON`.
3. Conecta `LLM.Message` -> `Type Convert.Input`.
4. Salida que se usará en el siguiente nodo: `Type Convert.JSON`.

## 4.4 Parser
Para que se usa:
- Extraer campos individuales del JSON para separar control de seguridad y ejecución de consulta.

Que recibe:
- `Type Convert.JSON`.

Que entrega:
- Valores extraidos en `Message output` (segun configuracion del parser).

Compatibilidad de UI (muy importante):
1. Variante A (UI con campos tipados): define campos `query`, `safe`, `reason` y conecta cada salida al nodo destino.
2. Variante B (UI con `Root path`, `Mode`, `Template`, `Separator`): crea 3 nodos parser:
- `ParserQuery`: `Root path = query`, `Mode = Stringify`, `Template = {text}` (o vacio), `Separator = vacio`.
- `ParserSafe`: `Root path = safe`, `Mode = Stringify`, `Template = {text}` (o vacio), `Separator = vacio`.
- `ParserReason`: `Root path = reason`, `Mode = Stringify`, `Template = {text}` (o vacio), `Separator = vacio`.

Conexion recomendada para variante B:
1. `Type Convert.JSON` -> `ParserQuery.Input`
2. `Type Convert.JSON` -> `ParserSafe.Input`
3. `Type Convert.JSON` -> `ParserReason.Input`

Error comun:
- Usar template `Text: {text}` en `ParserQuery`. Eso agrega prefijo y rompe el SQL.

## 4.5 SQL query
Para que se usa:
- Ejecutar en la base de datos únicamente la consulta SQL construida por el pipeline.

Que recibe:
- Un string SQL desde parser (consulta final).

Que entrega:
- Resultado en `JSON` para el prompt final.

Como configurarlo:
- Selecciona `DS_LAB202_MATCH_SQL` en `Select database` y activa `Include columns`.

1. `Select database`: `DS_LAB202_MATCH_SQL`.
2. `Include columns`: activado.
3. Conexion del SQL segun UI:
- Variante A: `Parser.query` -> `SQL query.Query`
- Variante B: `ParserQuery.Message` -> `SQL query.Query`

## 4.6 Prompt final
Para que se usa:
- Unificar pregunta, SQL ejecutado y resultados para que la respuesta final sea trazable y controlada.

Que recibe:
- Pregunta original, SQL, `safe`, `reason`, datos de consulta.

Que entrega:
- `Prompt message` final para el agente narrador.

Template:

```text
Eres un asistente de analítica de fútbol.

Pregunta:
{{question}}

SQL ejecutado:
{{sql}}

safe:
{{safe}}

reason:
{{reason}}

Datos:
{{datos}}

Instrucciones:
1) Responde en el idioma del usuario.
2) Si safe es false, responde breve y no intentes inferir.
3) Usa únicamente los datos de {{datos}}.
4) Si no hay filas, dilo explícitamente.
5) Incluye tabla cuando haya filas.
6) Muestra el SQL al final.
```

Conexiones:
1. `Chat input.Message` -> `question`
2. Campo SQL:
- Variante A: `Parser.query` -> `sql`
- Variante B: `ParserQuery.Message` -> `sql`
3. Campo safe:
- Variante A: `Parser.safe` -> `safe`
- Variante B: `ParserSafe.Message` -> `safe`
4. Campo reason:
- Variante A: `Parser.reason` -> `reason`
- Variante B: `ParserReason.Message` -> `reason`
5. `SQL query.JSON` -> `datos`

## 4.7 Agent + salida (Gate C)
Para que se usa:
- Transformar el contexto final en una respuesta clara para usuario y publicarla en el chat.

1. `Agent` con modelo `openai.gpt-oss-120b (oci)`.
2. Temperature: `0.2`.
3. `Prompt final.Prompt message` -> `Agent.Prompt`.
4. `Agent.Message` -> `Chat output.Message`.

Criterio de pase:
1. Este criterio se valida ejecutando el flujo en `Playground` y revisando la salida de cada nodo.
1. `Type Convert.JSON` no llega vacio.
2. El parser de SQL entrega una sentencia `SELECT` limpia.
3. `SQL query` ejecuta y devuelve JSON sin error.
4. `safe` y `reason` llegan al `Prompt final`.

No avances a publicación si este gate falla.

## 6) Troubleshooting

## 6.1 COPY_DATA falla
1. Consultar `USER_LOAD_OPERATIONS`.
2. Validar URL, delimitador, quote y charset.
3. Usar Opción B manual (Data Load) si persiste.

## 6.2 JSON inválido del LLM
1. Ver salida cruda de `LLM.Message`.
2. Endurecer prompt SQL con `Output ONLY valid JSON`.
3. Verificar llaves y comillas.

## 6.3 Parser no extrae `query`
1. Revisar mapeo de campos en Parser.
2. Confirmar claves exactas: `query`, `safe`, `reason`.

## 6.4 SQL inválido
1. Revisar si salió texto extra.
2. Confirmar ausencia de `;` y comentarios.
3. Confirmar que inicia con `SELECT`.

## 6.5 No hay datos
1. `SELECT COUNT(*) FROM ADMIN.LAB202_MATCH_FACT`.
2. Confirmar datasource apunta a la misma base.

## 6.6 Login/Session Agent Factory falla con `DPY-4001`/`ORA-01005`
1. Seguir el runbook operativo:
- `RUNBOOK-DPY-4001-ORA-01005-login-Agent-Factory.temp.md`
2. Ejecutar `loginValidation` y revisar logs backend antes de reinstalar.
